## 1. 컴파일 4단계 개요

평소 `gcc -o hello hello.c` 한 줄로 끝나지만, 내부에서는 4단계가 순서대로 실행된다.

```
hello.c ──전처리──> hello.i ──컴파일──> hello.s ──어셈블──> hello.o ──링크──> hello
(C 소스)   -E     (펼쳐진 C)   -S     (어셈블리)   -c    (목적 파일)   -o   (실행 파일)
```

| 단계 | 옵션 | 입력 → 출력 | 담당 | 하는 일 |
|---|---|---|---|---|
| ① 전처리 | `-E` | `.c` → `.i` | 전처리기 (cpp) | `#include` 펼치기, `#define` 치환, 주석 제거 |
| ② 컴파일 | `-S` | `.i` → `.s` | 컴파일러 (cc1 / clang) | C 코드를 어셈블리어로 번역, 최적화 |
| ③ 어셈블 | `-c` | `.s` → `.o` | 어셈블러 (as) | 어셈블리를 기계어로 변환 (목적 파일) |
| ④ 링크 | `-o` | `.o` → 실행 파일 | 링커 (ld) | 목적 파일 + 라이브러리 연결, `main` 확인 |

**핵심:** `-E`, `-S`, `-c`는 "그 단계까지만 하고 멈춰라"라는 뜻이다.

## 2. 단계별 실습

### 실습용 코드 — `hello.c`

```c
#include <stdio.h>

int main(void) {
    printf("Hello, World!\n");
    return 0;
}
```

### 명령어

```bash
gcc -E hello.c -o hello.i   # ① 전처리 결과를 파일로 저장
gcc -S hello.c              # ② hello.s 생성
gcc -c hello.c              # ③ hello.o 생성
gcc -o hello hello.o        # ④ 링크 → 실행 파일 hello
./hello                     # 실행 → Hello, World!
```

> `-E` 출력은 수백 줄이라 터미널에 그냥 찍으면 도배된다. `-o hello.i`로 저장해서 보는 게 좋다.

### 각 단계에서 관찰한 것

**① 전처리 (`-E`)**
- `#include <stdio.h>`가 `stdio.h`, `_stdio.h`, `_types.h` 등 여러 헤더로 연쇄적으로 펼쳐진다.
- `typedef` 선언들, `FILE` 구조체, `printf` / `puts` 등의 **함수 선언(프로토타입)** 이 들어온다.
- 맨 마지막에 내가 작성한 `main` 코드가 그대로 붙어 있다.
- `# 1 "hello.c"` 같은 줄은 **라인 마커**로, 원본 파일명·줄 번호 정보다 (에러 메시지에 원래 위치를 표시하기 위함).

**② 컴파일 (`-S`)**
- 사람이 읽을 수 있는 **텍스트 어셈블리** 파일이 생긴다.
- 문자열 `"Hello, World!\n"`은 별도 데이터 섹션에 저장된다.

**③ 어셈블 (`-c`)**
- **바이너리** 파일이라 에디터로 열면 깨져 보인다.
- `printf`의 실제 코드는 아직 없다. "여기서 printf를 호출할 예정"이라는 표시(미해결 심볼)만 있다.

**④ 링크 (`-o`)**
- `hello.o` + C 표준 라이브러리를 연결해서 실행 파일을 만든다.
- 프로그램 시작점인 `main`이 없으면 **이 단계에서** 에러가 난다.

## 3. 최적화 옵션과 어셈블리 관찰

### 교재 명령어 (p.43-44)

```bash
gcc -Wall -Werror -O2 -std=c99 -S helloworld.c
```

| 옵션 | 의미 |
|---|---|
| `-Wall` | 대부분의 경고 켜기 (Warning all) |
| `-Werror` | 경고를 에러로 취급 → 경고 하나라도 있으면 컴파일 실패 |
| `-O2` | 최적화 레벨 2 (**대문자 O** + 숫자 2) |
| `-std=c99` | C99 표준으로 컴파일 |
| `-g` | 디버깅 정보 포함 (gdb / lldb 사용 시) |

### 최적화 레벨

| 옵션 | 의미 |
|---|---|
| `-O0` | 최적화 없음 (기본값) — 디버깅하기 쉬움 |
| `-O1` | 기본 최적화 |
| `-O2` | 더 강한 최적화 — 일반적으로 배포용 |
| `-O3` | 최대 최적화 |

### 관찰 포인트: 컴파일러가 코드를 바꿔 버린다

`-O2`로 컴파일하면 교재의 Linux gcc 출력은 다음과 같다.

```asm
.LC0:
    .string "Hello, world!"      ; ← 문자열 끝의 \n이 사라짐!
main:
    leaq    .LC0(%rip), %rdi     ; ← 첫 번째 인자(rdi)에 문자열 주소
    subq    $8, %rsp
    call    puts@PLT             ; ← printf가 아니라 puts 호출!
    xorl    %eax, %eax           ; ← return 0 (eax = 0)
    addq    $8, %rsp
    ret
```

컴파일러가 알아낸 것:
1. 출력하는 것이 **고정된 문자열**이다 (`%d` 같은 포맷 지정자 없음)
2. 그 문자열이 **줄바꿈(`\n`)으로 끝난다**
3. → `puts()`는 자동으로 줄바꿈을 붙여 주므로, `printf("...\n")` 대신 **`puts("...")`로 바꿔도 결과가 같다**
4. `puts`가 포맷 해석을 안 하므로 더 빠르다

**교훈:** 컴파일러는 C 코드를 글자 그대로 번역하지 않고, 의미가 같은 더 효율적인 코드로 바꾼다.

### 어셈블리 읽기 기초 (x86-64, AT&T 문법)

| 명령 | 의미 |
|---|---|
| `leaq A, B` | A의 **주소**를 B에 저장 (load effective address) |
| `movq A, B` | A의 값을 B로 복사 (AT&T는 `출발, 도착` 순서) |
| `call f` | 함수 f 호출 |
| `xorl %eax, %eax` | 자기 자신과 XOR → 0. `return 0`의 관용 표현 |
| `ret` | 함수 반환 |
| `%rdi` | 함수의 **첫 번째 인자**를 담는 레지스터 |
| `%eax` / `%rax` | 함수의 **반환값**을 담는 레지스터 |

## 4. 동적 링킹 확인 (ldd / otool)

`hello.o`에는 `printf` / `puts`의 실제 코드가 없는데 실행이 된다. 실제 코드는 **실행 시점에 공유 라이브러리에서 불러오기** 때문이다 → **동적 링킹**.

실행 파일이 어떤 공유 라이브러리에 의존하는지 보는 명령:

```bash
# Linux
ldd helloworld

# macOS (ldd 없음!)
otool -L helloworld
```

### 출력 비교

**Linux**
```
linux-vdso.so.1 (0x00007ffd...)
libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f...)
/lib64/ld-linux-x86-64.so.2 (0x00007f...)
```

**macOS (실제 실습 결과)**
```
helloworld:
        /usr/lib/libSystem.B.dylib (compatibility version 1.0.0, current version 1351.0.0)
```

| 항목 | Linux | macOS |
|---|---|---|
| 확인 명령 | `ldd` | `otool -L` |
| 공유 라이브러리 확장자 | `.so` | `.dylib` |
| C 표준 라이브러리 | `libc.so.6` | `libSystem.B.dylib` (libc, libm 등을 하나로 묶음) |
| 동적 로더 | `ld-linux-x86-64.so.2` | `dyld` |

### 정적 링킹 vs 동적 링킹

| 구분 | 정적 링킹 | 동적 링킹 |
|---|---|---|
| 라이브러리 코드 위치 | 실행 파일 안에 복사 | 실행 시 외부에서 불러옴 |
| 실행 파일 크기 | 큼 | 작음 |
| 라이브러리 업데이트 | 다시 빌드해야 반영 | 자동 반영 |
| 라이브러리 없는 환경 | 실행 가능 | 실행 불가 |

## 5. 포인터와 어셈블리

> 교재 p.18 — Intel 표기 (`명령 도착, 출발` 순서)

### 핵심: `[ ]` = "그 주소에 있는 메모리"

| 표기 | 의미 | C로 치면 |
|---|---|---|
| `0x1234` | 숫자 0x1234 그 자체 | `0x1234` |
| `[0x1234]` | 0x1234번지 메모리에 들어 있는 값 | `*(int *)0x1234` |
| `RAX` | RAX 레지스터의 값 | 변수 값 |
| `[RAX]` | RAX 값을 주소로 보고 그 번지의 값 | `*ptr` |

**비유:** 메모리 = 번호 붙은 사물함. 주소 = 사물함 번호, `[주소]` = 사물함 안의 내용물.

### 예제 1: 변수와 포인터

```c
int x = 42;
int *px = &x;
```
```asm
MOV EAX, 42
MOV DWORD [0x1234], EAX    ; x의 주소(0x1234)에 42 저장
MOV RBX, 0x1234            ; RBX ← 숫자 0x1234 (x의 주소)
MOV QWORD [0x1240], RBX    ; px의 주소(0x1240)에 x의 주소 저장
```

실행 후 메모리:

| 주소 | 변수 | 값 |
|---|---|---|
| 0x1234 | `x` | `42` |
| 0x1240 | `px` | `0x1234` (x의 주소) |

→ **포인터도 메모리에 자기 자리를 가진 평범한 변수**이고, 안에 든 값이 "다른 변수의 주소"일 뿐이다.

### 예제 2: 역참조

```c
int *py = (int *)0x5678;
*py = 0xAABB;
```
```asm
MOV RAX, 0x5678            ; py = 0x5678
MOV DWORD [RAX], 0xAABB    ; *py = 0xAABB  (RAX가 가리키는 곳에 저장)
```

| C | 어셈블리 | 의미 |
|---|---|---|
| `py` | `RAX` | 주소 자체 |
| `*py` | `[RAX]` | 그 주소에 있는 값 |

**정리: C의 역참조 `*` = 어셈블리의 `[ ]`**

### 데이터 크기 지시어

| 지시어 | 크기 | 대응 C 타입 (x86-64) | 레지스터 |
|---|---|---|---|
| `BYTE` | 1바이트 | `char` | `AL` |
| `WORD` | 2바이트 | `short` | `AX` |
| `DWORD` | 4바이트 | `int` | `EAX` |
| `QWORD` | 8바이트 | `long`, **포인터** | `RAX` |

## 6. 헤더 파일과 include 경로

과제에서 직접 만든 헤더(예: `학번.h`)를 포함하는 방법.

| 표기 | 찾는 위치 | 용도 |
|---|---|---|
| `#include <stdio.h>` | 시스템 헤더 경로 | 표준 라이브러리 |
| `#include "학번.h"` | **현재 디렉터리 먼저**, 그다음 시스템 경로 | 내가 만든 헤더 |

- 과제에서는 `#include "학번.h"` 사용
- 꺾쇠 `<학번.h>`로 쓰고 싶다면 `-I.` 옵션으로 현재 디렉터리를 include 경로에 추가해야 한다

```bash
gcc -I. -o main main.c
```

- Makefile에서는 `CFLAGS=-I.`가 같은 역할 (04-Make 강의)

## 7. macOS vs Linux 차이

macOS의 `gcc`는 실제로는 **clang**이다 (`gcc --version`으로 확인 가능). 그래서 에러 메시지가 `clang: error`로 나온다.

| 항목 | Linux (gcc) | macOS (clang) |
|---|---|---|
| 실제 컴파일러 | GNU gcc | Apple clang |
| 함수 심볼 이름 | `main` | `_main` (앞에 `_` 붙음) |
| 문자열 섹션 | `.section .rodata` | `.section __TEXT,__cstring` |
| 문자열 라벨 | `.LC0:` | `L_.str:` |
| 문자열 지시어 | `.string` | `.asciz` |
| puts 호출 | `call puts@PLT` | `callq _puts` |
| 실행 파일 형식 | ELF | Mach-O |
| 의존성 확인 | `ldd` | `otool -L` |
| 공유 라이브러리 | `.so` | `.dylib` |

표기만 다르고 **개념은 동일**하다. 교재 출력과 비교할 때 참고.

## 8. 실습 중 겪은 에러 & 해결

| 에러 메시지 | 원인 | 해결 |
|---|---|---|
| `Undefined symbols: "_main"` | `hello.c`가 **빈 파일**이었음 (저장 안 함 / `touch`로 만든 빈 파일) | 코드 작성 후 저장. `cat hello.c` 또는 `ls -l`로 확인 |
| `unknown argument: '-02'` | 숫자 **0**을 입력함 | 대문자 **O**: `-O2` |
| `no such file or directory: 'hellowrold.c'` | 파일명 오타 | `ls`로 파일명 확인 |
| `no such file or directory: '#include'` | `-E` 뒤에 파일명이 아닌 지시어를 넣음 | `gcc -E hello.c` |
| `no such file or directory: 'E'` | `gcc - E` (하이픈 뒤 공백) | 붙여 쓰기: `-E` |
| `ld: warning: -s is obsolete` | 소문자 `-s`는 심볼 제거(strip) 옵션 | 어셈블리 생성은 대문자 `-S` |
| `zsh: command not found: ldd` | macOS에는 `ldd` 없음 | `otool -L helloworld` |

### 배운 점: 빈 파일은 링크 단계에서만 실패한다

빈 `hello.c`로 실습했을 때:

| 단계 | 결과 |
|---|---|
| `-E` | 라인 마커만 출력 (내용 없음) — **여기서 이미 빈 파일임을 알 수 있었음** |
| `-S` | 에러 없음 (빈 `.s`) |
| `-c` | 에러 없음 (빈 `.o`) |
| `-o` | **`_main` 없음 에러** |

→ 빈 파일은 문법 오류가 아니므로 컴파일은 통과한다. **`main` 존재 여부를 검사하는 것은 컴파일러가 아니라 링커**다.

### 대소문자 헷갈리는 옵션 모음

| 옵션 | 의미 |
|---|---|
| `-S` (대문자) | 어셈블리 생성 |
| `-s` (소문자) | 심볼 제거 |
| `-O2` (대문자 O) | 최적화 |
| `-o` (소문자) | 출력 파일 이름 지정 |
| `-E` (대문자) | 전처리만 |
| `-c` (소문자) | 목적 파일까지만 |

## 9. 교재 오류 정정

| 위치 | 교재 내용 | 정정 |
|---|---|---|
| p.43-44 보충 | "원본 슬라이드의 `02`가 아니라 `-02`가 맞다" | **`-O2` (대문자 알파벳 O)** 가 맞음. 숫자 0이면 `unknown argument` 에러 |
| p.18 | `MOV DWORD [0x1234], RAX` | DWORD(4B)에 RAX(8B)는 크기 불일치 → `EAX` 사용 |
| p.18 | `MOV DWORD [0x1240], RBX` | 64비트 포인터는 8바이트 → `QWORD` 사용 |

> p.18은 개념 설명용 단순화로 보이지만, 실제 어셈블러에서는 에러가 난다.

## 10. O/X 복습 문제

| # | 문제 | 답 |
|---|---|---|
| 1 | `#include`는 컴파일 단계에서 처리된다 | **X** — 전처리 단계 |
| 2 | `.o` 파일은 바로 실행할 수 있다 | **X** — 링크 전 미완성 파일 |
| 3 | `gcc -S`의 결과물은 텍스트 파일이다 | **O** |
| 4 | `printf`의 실제 코드는 `hello.o` 안에 있다 | **X** — 라이브러리에 있음 |
| 5 | `main`이 없으면 컴파일 단계에서 에러가 난다 | **X** — 링크 단계에서 에러 |
| 6 | `-O2`에서 컴파일러가 `printf("hi\n")`를 `puts("hi")`로 바꿀 수 있다 | **O** |
| 7 | macOS에서도 `ldd`로 공유 라이브러리를 확인한다 | **X** — `otool -L` |
| 8 | 어셈블리의 `[RAX]`는 C의 `*ptr`에 해당한다 | **O** |
| 9 | 포인터 변수도 메모리에 자기 주소를 가진다 | **O** |
| 10 | `MOV RBX, 0x1234`는 0x1234번지의 값을 RBX에 넣는다 | **X** — 숫자 0x1234 자체를 넣음 |
| 11 | `#include "a.h"`는 현재 디렉터리를 먼저 찾는다 | **O** |
| 12 | x86-64에서 함수의 첫 번째 인자는 `%rdi`에 들어간다 | **O** |

## 한 줄 요약

> **`.c → .i → .s → .o → 실행파일`** (전처리 → 컴파일 → 어셈블 → 링크). 컴파일러는 최적화로 코드를 바꾸고, 라이브러리 코드는 실행 시 동적으로 연결된다. 포인터는 "주소를 담은 변수"이고, C의 `*`는 어셈블리의 `[ ]`다.

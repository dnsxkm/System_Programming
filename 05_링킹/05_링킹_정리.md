## 1. 링커가 필요한 이유

```
main.c ─(cpp, cc1, as)→ main.o ─┐
                                 ├─(ld)→ prog   완전히 링크된 실행 파일
sum.c  ─(cpp, cc1, as)→ sum.o  ─┘
        따로 컴파일된 재배치 가능 오브젝트 파일
```

| 이유 | 설명 |
|---|---|
| **모듈화** | 프로그램을 작은 소스 파일 여러 개로 나눠 작성. 자주 쓰는 함수는 라이브러리로 묶음 (예: 수학 라이브러리, C 표준 라이브러리) |
| **효율 (시간)** | 분리 컴파일: 파일 하나를 고치면 그 파일만 다시 컴파일하고 다시 링크. 나머지는 재컴파일 불필요 |
| **효율 (공간)** | 라이브러리에서 **실제로 쓰는 함수의 코드만** 실행 파일과 메모리에 들어감 |

## 2. 오브젝트 파일 3종류와 ELF

| 종류 | 확장자 | 설명 | `e_type` |
|---|---|---|---|
| **재배치 가능** 오브젝트 | `.o` | 다른 `.o`와 합쳐 실행 파일을 만들 수 있는 형태. `.c` 하나당 `.o` 하나 | `ET_REL` (1) |
| **실행 가능** 오브젝트 | `a.out` | 메모리에 그대로 복사해 실행할 수 있는 형태 | `ET_EXEC` (2), PIE면 `ET_DYN` (3) |
| **공유** 오브젝트 | `.so` | 로드 시점이나 실행 중에 동적으로 링크되는 특수한 재배치 파일. Windows에선 DLL | `ET_DYN` (3) |

세 가지 모두 **ELF**(Executable and Linkable Format) 한 가지 형식이다.

| 섹션 | 내용 |
|---|---|
| ELF header | 워드 크기, 바이트 순서, 파일 종류, 머신 종류 등 |
| Segment(Program) header table | 페이지 크기, 메모리 세그먼트의 가상주소와 크기 (**실행 파일에 필수**) |
| `.text` | 기계어 코드 |
| `.rodata` | 읽기 전용 데이터: 문자열 상수, switch 점프 테이블 |
| `.data` | **초기화된** 전역 변수 |
| `.bss` | **초기화 안 된** 전역 변수. 섹션 헤더만 있고 파일 공간은 0 ("Better Save Space") |
| `.symtab` | 심볼 테이블: 함수와 static 변수 이름, 섹션과 위치 |
| `.rel.text` | `.text`에서 링크할 때 고쳐야 할 명령어 주소와 고치는 방법 |
| `.rel.data` | `.data`에서 고쳐야 할 포인터 데이터 주소 |
| `.debug` | 디버깅 정보 (`gcc -g`) |
| Section header table | 각 섹션의 오프셋과 크기 (**재배치 파일에 필수**) |

> ELF 헤더를 바이트 단위로 직접 읽어 본 내용은 [과제 2 스터디 노트](../Assignment_2/ELF_스터디노트.html)에 있다.

## 3. 링커의 일 ① 심볼 해석 — `01_정적_링킹/`

```c
// main.c
int sum(int *a, int n);         // 외부 심볼: sum.c에 정의됨
int array[2] = {1, 2};          // 전역 심볼, 초기값 있음 → .data

int main(void)
{
    int val = sum(array, 2);    // val은 지역 변수 → 링커는 모름
    return val;
}
```

```c
// sum.c
int sum(int *a, int n)          // 전역 심볼: main.c에서 참조
{
    int i, s = 0;               // 지역 변수 → 링커 심볼 아님
    for (i = 0; i < n; i++) {
        s += a[i];
    }
    return s;
}
```

**심볼 해석**: 프로그램은 심볼(전역 변수와 함수)을 정의하고 참조한다. 어셈블러가 정의를 `.symtab`(구조체 배열: 이름, 크기, 위치)에 기록하고, 링커는 **각 참조를 정확히 하나의 정의에 연결**한다.

```bash
gcc -Og -c main.c sum.c         # 교재와 비슷한 코드가 나오도록 -Og
gcc -o prog main.o sum.o
./prog; echo "exit=$?"          # exit=3  (1 + 2)
readelf -s main.o
```

```
     3: 0000000000000000    24 FUNC    GLOBAL DEFAULT    1 main
     4: 0000000000000000     8 OBJECT  GLOBAL DEFAULT    3 array
     5: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT  UND sum
```

- `main`, `array`는 main.o가 **정의**한 전역 심볼이다 (섹션 1 = `.text`, 3 = `.data`).
- `sum`은 `UND`(undefined): main.o는 **참조만** 하고, 정의는 링크할 때 sum.o에서 찾는다.
- `val`, `i`, `s`는 심볼 테이블에 없다. 스택에 있는 지역 변수는 링커가 모른다.

### 심볼의 종류

| 종류 | 정의 | 예 |
|---|---|---|
| **전역** 심볼 | 모듈 m이 정의하고 다른 모듈이 참조할 수 있음 | static이 아닌 함수, static이 아닌 전역 변수 |
| **외부** 심볼 | 모듈 m이 참조하지만 다른 모듈이 정의함 | main.c의 `sum` |
| **지역** 심볼 | 모듈 m 안에서만 정의되고 참조됨 | `static` 함수, `static` 전역 변수 |

> **지역 링커 심볼 ≠ 지역 프로그램 변수.** 함수 안의 일반 지역 변수는 스택에 있어 심볼이 아니다. 함수 안의 `static` 변수는 `.data`/`.bss`에 있고 **지역 심볼**이 된다.

```c
// static_local.c
int f(void) { static int x = 0; return x; }   // .bss
int g(void) { static int x = 1; return x; }   // .data
```

```
$ readelf -s static_local.o | grep " x"
     5: 0000000000000000     4 OBJECT  LOCAL  DEFAULT    4 x.1
     6: 0000000000000000     4 OBJECT  LOCAL  DEFAULT    3 x.0
```

이름이 같은 `x` 두 개가 `x.0`, `x.1`처럼 **고유한 이름의 지역 심볼**이 되고, 섹션도 다르다 (4 = `.bss`, 3 = `.data`).

## 4. 링커의 일 ② 재배치 — `objdump -r`

**재배치**: 각 `.o`의 같은 섹션(`.text`끼리, `.data`끼리)을 하나로 **합치고**, 심볼을 `.o` 안의 상대 위치에서 실행 파일의 **최종 주소로 옮긴 뒤**, 그 심볼을 가리키던 **모든 참조를 고친다**.

### 링크 전 (`main.o`)

```
$ objdump -r -d main.o
0000000000000000 <main>:
   0:   48 83 ec 08             sub    $0x8,%rsp
   4:   be 02 00 00 00          mov    $0x2,%esi
   9:   bf 00 00 00 00          mov    $0x0,%edi        # %edi = &array (아직 모름 → 0)
                        a: R_X86_64_32  array            # 재배치 엔트리
   e:   e8 00 00 00 00          call   13 <main+0x13>   # sum() (아직 모름 → 0)
                        f: R_X86_64_PLT32       sum-0x4  # 재배치 엔트리
  13:   48 83 c4 08             add    $0x8,%rsp
  17:   c3                      ret
```

- 주소가 들어갈 자리가 `00 00 00 00`으로 비어 있다.
- 재배치 엔트리 = "**오프셋 a에 array의 절대 주소(32비트)**를 넣어라", "**오프셋 f에 sum의 PC 상대 주소 - 4**를 넣어라".
- 교재는 `R_X86_64_PC32`인데 최신 gcc는 함수 호출에 `R_X86_64_PLT32`를 쓴다. 정적 링크에서는 계산이 같다.

### 링크 후 (`prog`)

```
$ objdump -d prog
0000000000401106 <main>:
  401106:       48 83 ec 08             sub    $0x8,%rsp
  40110a:       be 02 00 00 00          mov    $0x2,%esi
  40110f:       bf 10 40 40 00          mov    $0x404010,%edi   # &array = 0x404010
  401114:       e8 05 00 00 00          call   40111e <sum>
  401119:       48 83 c4 08             add    $0x8,%rsp
  40111d:       c3                      ret

000000000040111e <sum>:
  ...
$ nm prog | grep -E " (main|sum|array)$"
0000000000404010 D array
0000000000401106 T main
000000000040111e T sum
```

| 재배치 | 계산 | 결과 |
|---|---|---|
| `R_X86_64_32 array` (절대) | `ADDR(array)` | `0x404010` → 리틀 엔디언으로 `10 40 40 00` |
| `R_X86_64_PLT32 sum-4` (PC 상대) | `ADDR(sum) + (-4) - 참조 위치` = `0x40111e - 4 - 0x401115` | `0x05` → `05 00 00 00` |

PC 상대 주소의 의미: `call`을 실행할 때 PC는 **다음 명령어**(0x401119)를 가리킨다. `0x401119 + 5 = 0x40111e` = sum. 그래서 addend가 -4(주소 필드 4바이트만큼)다.

### 실행 파일이 메모리에 올라간 모습

```
커널 메모리               ← 사용자 코드에서 안 보임
사용자 스택  (%rsp)       ← 실행 시 생성, 아래로 자람
     ↓
공유 라이브러리 매핑 영역
     ↑
런타임 힙 (malloc)        ← brk까지
읽기/쓰기 세그먼트 (.data, .bss)          ┐ 실행 파일에서
읽기 전용 세그먼트 (.init, .text, .rodata) ┘ 불러옴 (0x400000부터)
사용 안 함
0
```

## 5. 강한 심볼 vs 약한 심볼 — `02_강한_약한_심볼/`

| 구분 | 무엇 | 예 |
|---|---|---|
| **강한** 심볼 | 함수, **초기화된** 전역 변수 | `int foo = 5;`, `p1() {}` |
| **약한** 심볼 | **초기화 안 된** 전역 변수 | `int foo;` |

### 링커 규칙

| 규칙 | 상황 | 결과 |
|---|---|---|
| 1 | 같은 이름의 **강한 심볼이 여러 개** | **링크 에러** |
| 2 | 강한 심볼 1개 + 약한 심볼 여러 개 | **강한 심볼** 선택. 약한 심볼 참조도 강한 것으로 연결 |
| 3 | **약한 심볼만** 여러 개 | 그중 **아무거나** 선택 (`-fno-common`으로 막을 수 있음) |

### 링커 퍼즐 (슬라이드 17)

| 모듈 1 | 모듈 2 | 결과 |
|---|---|---|
| `int x; p1() {}` | `p1() {}` | 링크 에러: 강한 심볼 `p1` 두 개 |
| `int x; p1() {}` | `int x; p2() {}` | 두 `x`는 같은 변수 (원한 게 맞나?) |
| `int x; int y; p1() {}` | `double x; p2() {}` | p2의 `x` 쓰기가 **y를 덮어쓸 수 있음** |
| `int x=7; int y=5; p1() {}` | `double x; p2() {}` | p2의 `x` 쓰기가 **y를 덮어씀** |
| `int x=7; p1() {}` | `int x; p2() {}` | 둘 다 초기화된 그 변수를 가리킴 |

### 실습: `int x = 7; int y = 5;` vs `double x;`

```c
// p1.c
int x = 7;                      // 강한 심볼
int y = 5;                      // 강한 심볼
void p2(void);

int main(void)
{
    printf("before: x = %d, y = %d\n", x, y);
    p2();
    printf("after : x = %d, y = %d\n", x, y);
    return 0;
}
```

```c
// p2.c
double x;                       // 약한 심볼 (타입이 다름!)

void p2(void)
{
    x = -0.0;                   // 8바이트를 씀 → x(4B)와 y(4B)를 함께 덮어씀
}
```

**① 그냥 링크하면 (gcc 13)**

```
$ gcc -o pp p1.c p2.c
/usr/bin/ld: /tmp/cc0DCKsJ.o:(.bss+0x0): multiple definition of `x'; /tmp/ccYvYBDz.o:(.data+0x0): first defined here
collect2: error: ld returned 1 exit status
```

gcc 10부터 기본값이 **`-fno-common`**이라, 초기화 안 된 전역 `double x;`도 `.bss`에 자리를 갖는 **정의**가 된다. 그래서 규칙 1(강한 심볼 두 개)처럼 에러가 난다. 슬라이드의 "Can override this with gcc -fno-common"이 지금은 **기본 동작**이다.

**② `-fcommon`으로 옛날 동작을 켜면**

```
$ gcc -fcommon -o pp p1.c p2.c
/usr/bin/ld: warning: alignment 4 of symbol `x' in /tmp/ccPMwM1s.o is smaller than 8 in /tmp/ccWeCMMR.o
$ ./pp
before: x = 7, y = 5
after : x = 0, y = -2147483648
```

- 링커는 규칙 2에 따라 p1.c의 강한 `int x`를 고른다. 크기는 4바이트.
- p2.c는 그 자리를 8바이트 `double`로 알고 `-0.0`(비트 `0x8000000000000000`)을 쓴다.
- 리틀 엔디언이라 아래 4바이트 `00 00 00 00` → **x = 0**, 위 4바이트 `00 00 00 80` → 바로 뒤의 **y = 0x80000000 = -2147483648**.
- 경고 한 줄 말고는 에러 없이 실행되므로 찾기 어려운 버그가 된다.

### 전역 변수 사용 원칙 (슬라이드 18)

- 피할 수 있으면 피한다.
- 쓸 거면 `static`을 붙일 수 있는지 먼저 본다.
- 전역 변수를 **정의**할 때는 초기화한다 (강한 심볼로 만들어 충돌을 에러로 잡음).
- 다른 파일의 전역 변수를 **참조**할 때는 `extern`을 쓴다.

## 6. 정적 라이브러리 — `03_정적_라이브러리/`

자주 쓰는 함수를 어떻게 묶어 줄까?

| 방법 | 문제 |
|---|---|
| 모든 함수를 소스 파일 하나에 | 큰 오브젝트를 통째로 링크 → 공간·시간 낭비 |
| 함수마다 소스 파일 하나씩 | 효율적이지만, 프로그래머가 필요한 `.o`를 일일이 나열해야 함 |
| **정적 라이브러리 (`.a`)** | 관련된 `.o`들을 인덱스와 함께 **아카이브** 하나로 묶음. 링커는 미해결 참조를 해결하는 **멤버 `.o`만** 꺼내 링크 |

```bash
gcc -c addvec.c multvec.c
ar rs libvector.a addvec.o multvec.o     # r: 넣기(교체), s: 인덱스 생성
ar -t libvector.a                         # 목록 보기
gcc -c main2.c
gcc -static -o prog2c main2.o ./libvector.a
./prog2c
```

```
addvec.o
multvec.o
z = [4 6]
$ nm prog2c | grep -E " (addvec|multvec)$"
0000000000401756 T addvec
```

`main2.c`는 `addvec`만 호출하므로, 실행 파일에 **`addvec.o`만 들어가고 `multvec`은 없다.** `.a` 안에서도 필요한 `.o`만 골라 링크하기 때문이다. 아카이브는 일부만 고쳐 넣을 수 있어서(`ar r`), 함수 하나를 고치면 그 `.o`만 다시 컴파일해 교체하면 된다.

### 링커가 외부 참조를 해결하는 순서

1. 명령행에 나온 **순서대로** `.o`와 `.a`를 스캔한다.
2. 스캔하는 동안 **아직 해결 안 된 참조 목록**을 유지한다.
3. 새 파일을 만날 때마다 그 파일이 정의한 심볼로 목록의 참조를 해결해 본다. `.a`는 목록을 해결하는 멤버만 가져온다.
4. 끝까지 스캔한 뒤 목록에 남은 게 있으면 **에러**.

```
$ gcc -static -o bad ./libvector.a main2.o
/usr/bin/ld: main2.o: in function `main':
main2.c:(.text+0x19): undefined reference to `addvec'
collect2: error: ld returned 1 exit status
```

`libvector.a`를 먼저 스캔할 때는 미해결 목록이 비어 있어서 아무것도 가져오지 않는다. 그다음 `main2.o`가 `addvec`을 참조하지만 이미 지나간 뒤다. → **라이브러리는 명령행 맨 뒤에** 둔다.

`-l`/`-L` 옵션도 같다: `gcc -o prog main2.o -L. -lvector` (`-lvector` = `libvector.a` 또는 `libvector.so`를 `-L` 경로에서 찾음).

### 자주 쓰는 라이브러리

| 라이브러리 | 내용 |
|---|---|
| `libc.a` | C 표준 라이브러리. I/O, 메모리 할당, 시그널, 문자열, 날짜·시간, 난수, 정수 연산 (수천 개의 `.o`) |
| `libm.a` | 수학 라이브러리. `sin`, `cos`, `log`, `exp`, `sqrt` 등 실수 연산 |

## 7. 공유 라이브러리와 동적 링킹 — `04_공유_라이브러리/`

### 정적 라이브러리의 단점

- **디스크 중복**: 모든 실행 파일에 `printf` 같은 libc 코드가 복사됨.
- **메모리 중복**: 실행 중인 프로세스마다 같은 코드가 메모리에 따로 올라감.
- **업데이트**: 시스템 라이브러리 버그를 고쳐도 **모든 프로그램을 다시 링크**해야 반영됨.

```
$ ls -l prog2c prog2l
951680 prog2c      # -static: libc까지 전부 포함
 15904 prog2l      # 기본(동적 링킹): libc.so는 실행할 때 연결
```

### 공유 라이브러리 (`.so`)

코드와 데이터를 **로드 시점** 또는 **실행 중**에 프로그램에 동적으로 불러와 링크하는 오브젝트 파일. 여러 프로세스가 **같은 코드를 공유**할 수 있다 (9강 가상메모리에서 원리를 배움).

```bash
gcc -shared -fpic -o libvector.so addvec.c multvec.c   # -fpic: 위치 독립 코드
gcc -o prog2d main2.c ./libvector.so
./prog2d
ldd prog2d
```

```
z = [4 6]
        ./libvector.so (0x00007fffff7c3000)
        libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007fffff5da000)
        /lib64/ld-linux-x86-64.so.2 (0x00007ffffffcb000)
```

| 시점 | 누가 | 어떻게 |
|---|---|---|
| **로드 타임** 링킹 | 동적 링커 `ld-linux.so` | 실행 파일을 처음 로드할 때(`execve`) 자동으로. libc는 보통 이 방식 |
| **런타임** 링킹 | 프로그램 코드 | 실행 중에 `dlopen()` 호출. 소프트웨어 배포, 고성능 웹 서버, 런타임 인터포지셔닝에 사용 |

동적 링크된 실행 파일에는 정적 링크 파일에 없는 섹션이 생긴다.

```
$ readelf -S prog2d
  [ 1] .interp     PROGBITS   ...   # 동적 링커 경로
  [ 6] .dynsym     DYNSYM     ...   # 동적 심볼 테이블
  [21] .dynamic    DYNAMIC    ...   # 필요한 .so 목록 등
$ readelf -p .interp prog2d
  [     0]  /lib64/ld-linux-x86-64.so.2
```

### 실행 중에 불러오기: `dlopen` / `dlsym` / `dlclose` (`dll.c`)

```c
handle = dlopen("./libvector.so", RTLD_LAZY);   // 라이브러리 로드 (함수는 처음 호출할 때 해석)
addvec = dlsym(handle, "addvec");               // 이름으로 함수 주소 얻기
addvec(x, y, z, 2);                             // 일반 함수처럼 호출
dlclose(handle);                                // 해제
// 에러 메시지는 dlerror()로
```

```
$ gcc -rdynamic -o progr dll.c -ldl
$ ./progr
z = [4 6]
```

### 링킹이 일어나는 세 시점 (요약)

| 시점 | 담당 |
|---|---|
| 컴파일 타임 | 링커 (`ld`) |
| 로드 타임 | 로더 (`execve`) + 동적 링커 |
| 런타임 | 프로그램 코드 (`dlopen`) |

## 8. 라이브러리 인터포지셔닝 — `05_인터포지셔닝/`

**인터포지셔닝**: 임의의 함수 호출을 **가로채는** 링킹 기법. 소스 코드를 고치지 않고 `malloc`/`free`를 추적해 보자.

```c
// int.c (대상 프로그램, 고치지 않음)
#include <stdio.h>
#include <malloc.h>

int main(void)
{
    int *p = malloc(32);
    free(p);
    return 0;
}
```

쓰임새: 보안(샌드박싱, 몰래 암호화), 디버깅(Facebook 엔지니어들이 `write` 계열을 가로채 1년 묵은 버그를 찾음), 모니터링·프로파일링(호출 횟수 세기, malloc 추적, 메모리 누수 탐지).

### ① 컴파일 타임: 매크로로 바꿔치기

```c
// malloc.h (내가 만든 헤더)
#define malloc(size) mymalloc(size)
#define free(ptr) myfree(ptr)
void *mymalloc(size_t size);
void myfree(void *ptr);
```

```
$ gcc -DCOMPILETIME -c mymalloc.c
$ gcc -I. -o intc int.c mymalloc.o     # -I. : 내 malloc.h를 시스템 것보다 먼저 찾음
$ ./intc
malloc(32)=0x4052a0
free(0x4052a0)
```

전처리 단계에서 `malloc(32)`가 `mymalloc(32)`로 바뀐다. **소스를 다시 컴파일**해야 한다.

### ② 링크 타임: `--wrap`

```c
void *__real_malloc(size_t size);       // 링커가 진짜 malloc으로 연결
void *__wrap_malloc(size_t size)        // 프로그램의 malloc 호출이 여기로 옴
{
    void *ptr = __real_malloc(size);
    printf("malloc(%d) = %p\n", (int)size, ptr);
    return ptr;
}
```

```
$ gcc -DLINKTIME -c mymalloc.c
$ gcc -c int.c
$ gcc -Wl,--wrap,malloc -Wl,--wrap,free -o intl int.o mymalloc.o
$ ./intl
malloc(32) = 0x4052a0
free(0x4052a0)
```

- `-Wl,옵션`은 옵션을 링커에 넘긴다 (쉼표는 공백으로 바뀜).
- `--wrap,malloc`: `malloc` 참조 → `__wrap_malloc`, `__real_malloc` 참조 → 진짜 `malloc`.
- `.o`는 그대로 두고 **다시 링크**만 하면 된다.

### ③ 로드/런타임: `LD_PRELOAD`

```c
#define _GNU_SOURCE
#include <dlfcn.h>

void *malloc(size_t size)               // libc와 같은 이름으로 정의
{
    void *(*mallocp)(size_t size);
    mallocp = dlsym(RTLD_NEXT, "malloc");   // 검색 순서상 "다음" malloc = libc의 것
    void *ptr = mallocp(size);
    printf("malloc(%d) = %p\n", (int)size, ptr);
    return ptr;
}
```

```
$ gcc -DRUNTIME -shared -fpic -o mymalloc.so mymalloc.c -ldl
$ gcc -o intr int.c
$ LD_PRELOAD=./mymalloc.so ./intr
malloc(32) = 0x4052a0
free(0x4052a0)
$ ./intr                                # LD_PRELOAD 없이는 아무 출력 없음
```

- `LD_PRELOAD` 환경 변수: 동적 링커(`ld-linux.so`)가 미해결 참조(`malloc`)를 **`mymalloc.so`에서 먼저** 찾게 한다.
- 실행 파일을 **다시 컴파일도, 링크도 하지 않는다.**
- 주의: `printf`가 내부에서 `malloc`을 부를 수 있어 무한 재귀가 생길 수 있다. 그래서 실습 코드에는 `calling` 플래그로 재귀를 막아 두었다.

### 세 방법 비교

| 시점 | 방법 | 다시 해야 하는 것 | 핵심 |
|---|---|---|---|
| 컴파일 타임 | `#define malloc(size) mymalloc(size)` + `-I.` | 소스 재컴파일 | 매크로 확장으로 호출 대상이 바뀜 |
| 링크 타임 | `-Wl,--wrap,malloc` | 재링크 | `malloc` → `__wrap_malloc`, `__real_malloc` → `malloc` |
| 로드/런타임 | `LD_PRELOAD` + `dlsym(RTLD_NEXT, ...)` | 없음 | 동적 링커가 내 `.so`를 먼저 검색 |

## 9. 실습 중 겪은 에러 & 해결

| 에러 메시지 | 원인 | 해결 |
|---|---|---|
| `multiple definition of 'x'` | gcc 10+ 기본값 `-fno-common`. `double x;`도 정의가 됨 | 슬라이드 퍼즐을 재현하려면 `-fcommon`. 실제 코드에선 에러가 나는 게 맞음 |
| `alignment 4 of symbol 'x' ... is smaller than 8` (경고) | `-fcommon`에서 `int x`(4B)와 `double x`(8B)가 합쳐짐 | 경고를 무시하면 y가 덮어써짐. 타입을 맞추고 `extern` 사용 |
| `warning: pointer 'ptr' used after 'free' [-Wuse-after-free]` (COMPILETIME) | 강의 코드의 `myfree`가 `free(ptr)` 뒤에 `ptr` 값을 출력 | 주소 값만 찍고 역참조하지 않아 동작은 안전. 경고를 없애려면 `free` 전에 출력 |
| `undefined reference to 'addvec'` | 라이브러리를 `.o`보다 **앞에** 둠 | 라이브러리를 명령행 맨 뒤로 |
| (macOS) `fatal error: 'malloc.h' file not found` | macOS에는 `<malloc.h>`가 없음 (`<stdlib.h>`에 선언) | Linux(Docker)에서 실습 |
| (macOS) `ld: unknown options: --wrap --wrap` | macOS 링커는 `--wrap`을 지원하지 않음 | Linux(Docker)에서 실습. macOS의 런타임 방식은 `DYLD_INSERT_LIBRARIES` |

## 10. O/X 복습 문제

| # | 문제 | 정답 |
|---|---|---|
| 1 | `.o`, 실행 파일, `.so`는 모두 ELF 형식이다 | **O** |
| 2 | 함수 안의 지역 변수 `int i`는 링커의 지역 심볼이다 | **X** — 스택에 있어 심볼이 아님. `static` 지역 변수만 심볼 |
| 3 | `int x;`(초기화 안 된 전역)는 강한 심볼이다 | **X** — 약한 심볼. 함수와 초기화된 전역이 강한 심볼 |
| 4 | 강한 심볼 1개와 약한 심볼 여러 개가 있으면 강한 심볼이 선택된다 | **O** |
| 5 | 재배치 전 `main.o`의 `call` 명령어에는 이미 `sum`의 주소가 들어 있다 | **X** — `00 00 00 00`이고 재배치 엔트리가 따로 있음 |
| 6 | `R_X86_64_PC32`는 다음 명령어 주소 기준의 상대 거리를 채운다 | **O** |
| 7 | 정적 라이브러리를 링크하면 `.a` 안의 모든 `.o`가 실행 파일에 들어간다 | **X** — 미해결 참조를 해결하는 멤버만 |
| 8 | `gcc -lvector main.o`처럼 라이브러리를 앞에 써도 항상 링크된다 | **X** — 왼쪽부터 스캔하므로 실패할 수 있음 |
| 9 | 공유 라이브러리를 쓰면 라이브러리만 고쳐도 프로그램에 반영된다 | **O** — 다시 링크할 필요 없음 |
| 10 | `.bss` 섹션은 변수 크기만큼 파일 공간을 차지한다 | **X** — 섹션 헤더만 있고 파일 공간은 0 |
| 11 | 링크 타임 인터포지셔닝에서 `__real_malloc`은 진짜 libc `malloc`으로 연결된다 | **O** |
| 12 | `LD_PRELOAD`를 쓰려면 대상 프로그램을 다시 컴파일해야 한다 | **X** — 다시 컴파일도 링크도 안 함. 동적 링커가 처리 |

## 한 줄 요약

> 링커는 **심볼 해석**(참조 하나에 정의 하나)과 **재배치**(섹션 합치기 + 최종 주소로 참조 고치기)를 한다. 같은 이름이면 **강한 심볼**(함수, 초기화된 전역)이 이기고, 강한 것 둘은 에러다. 정적 라이브러리(`.a`)는 **필요한 `.o`만** 복사하고 **명령행 순서**가 중요하며, 공유 라이브러리(`.so`)는 **로드 타임**(`ld-linux.so`)이나 **런타임**(`dlopen`)에 연결된다. 함수 호출은 **컴파일**(`#define`), **링크**(`--wrap`), **로드**(`LD_PRELOAD`) 시점에 가로챌 수 있다.

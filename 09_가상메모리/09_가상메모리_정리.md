## 1. 물리 주소 vs 가상 주소

| 방식 | 동작 | 쓰는 곳 |
|---|---|---|
| **물리 주소** 방식 | CPU가 낸 주소(PA)로 바로 메인 메모리 접근 | 자동차·엘리베이터·디지털 액자의 마이크로컨트롤러 같은 단순한 시스템 |
| **가상 주소** 방식 | CPU가 낸 주소(VA)를 **MMU**가 물리 주소로 바꿔서 접근 | 모든 현대 서버, 노트북, 스마트폰. "컴퓨터 과학의 위대한 아이디어 중 하나" |

```
CPU ──VA 4100──→ [MMU] ──PA 4──→ 메인 메모리
     (CPU 칩 안)
```

**가상 메모리**: 프로그램이 보는 주소 공간을 실제 메모리의 물리적 배치와 **분리**하는 메커니즘. 가상 주소 = 프로그램 주소 공간의 위치, 물리 주소 = 실제 RAM의 위치. 둘이 같을 필요가 없다.

### 왜 가상 메모리인가

| 장점 | 설명 |
|---|---|
| 메인 메모리의 한계 극복 | 물리 메모리는 가상 메모리에 **실제로 접근할 때** 할당 → **게으른 할당 (lazy allocation)** |
| 메모리 보기 단순화 | 모든 프로세스가 **똑같은 모양의 선형 주소 공간**을 가짐 |
| 주소 공간 격리 | 한 프로세스가 다른 프로세스의 메모리를 건드릴 수 없음. 사용자 프로그램은 커널 정보와 코드에 접근 불가 |

### 모순처럼 보이는 사실들

- 모든 프로세스는 NULL 근처에 매핑되지 않은 메모리가 있다.
- 각 프로세스는 주소 공간 **전체**를 쓸 수 있는 것처럼 보인다.
- 그런데 각 프로세스는 **다른 프로세스의 메모리**에는 접근할 수 없다.
- 그런데 동적 라이브러리는 여러 프로세스가 **공유**한다.

→ 이걸 전부 가능하게 하는 게 가상 메모리다. 프로세스 주소 공간의 **모든 주소는 가상 주소**다.

### 물리 메모리 배치는 기계마다 다르다

- 특정 위치가 예약됨 (예: RAM 처음 4KB는 16비트 BIOS 영역)
- 장치가 메모리 주소 공간에 나타남 (예: PCI 장치 설정 영역)
- RAM 크기가 다름 (예: 내장 GPU가 시스템 RAM 일부를 VRAM으로 가져감)

예전에는 프로그램이 이런 제약을 알아야 했지만, 지금은 가상 메모리가 숨겨 준다. **커널은 여전히 물리 배치를 알아야 한다.**

## 2. 주소 공간과 MMU — `address.c`

| 용어 | 정의 |
|---|---|
| 선형 주소 공간 | 연속된 0 이상 정수 주소의 순서 있는 집합 `{0, 1, 2, ...}` |
| 가상 주소 공간 | N = 2^n개의 가상 주소 `{0, ..., N-1}` |
| 물리 주소 공간 | M = 2^m개의 물리 주소 `{0, ..., M-1}` |

- x86-64의 가상 주소 공간은 0 ~ 2^64 - 1. 옛 프로세서는 그중 **48비트**만, 최근 프로세서는 **52비트**까지 지원한다.
- 실제 하드웨어 메모리는 이보다 훨씬 작을 수 있다.

**MMU (Memory Management Unit)**: CPU가 주소에 접근할 때마다 그 주소를 가로채 **가상 주소 공간 → 물리 주소 공간**으로 바꾸고, 바뀐 주소로 RAM에 접근한다. 이것을 **주소 변환**이라 한다.

### 실습: 내 변수들의 가상 주소를 VPN / VPO로 나누기 (x86-64)

페이지 크기 P = 2^p바이트면, 가상 주소의 **아래 p비트 = VPO**(페이지 안 오프셋), **나머지 = VPN**(가상 페이지 번호).

```
$ ./address
page size = 4096 bytes (p = 12 bits)
code     VA = 0x0000004011bb  VPN = 0x000000401  VPO = 0x1bb
rodata   VA = 0x00000040206a  VPN = 0x000000402  VPO = 0x06a
.data    VA = 0x000000404030  VPN = 0x000000404  VPO = 0x030
.bss     VA = 0x000000404038  VPN = 0x000000404  VPO = 0x038
heap     VA = 0x0000004052a0  VPN = 0x000000405  VPO = 0x2a0
stack    VA = 0x7ffffffca95c  VPN = 0x7ffffffca  VPO = 0x95c
```

- 4KB = 2^12 → 16진수로 **마지막 3자리가 VPO**, 앞부분이 VPN이다.
- `.data`와 `.bss`는 **같은 페이지**(VPN 0x404)에 있다.
- 코드는 0x400000 근처부터, 스택은 주소 공간 꼭대기 근처에 있다. 5강 메모리 배치 그림 그대로다.

## 3. VM은 캐시 도구: 페이지와 페이지 테이블

### 큰 파일을 다루는 세 가지 방법 (슬라이드 14~16)

| 상황 | 방법 |
|---|---|
| 큰 파일을 처음부터 끝까지 | 작은 버퍼로 `read()`/`fread()`를 여러 번 |
| 큰 파일의 **아무 위치**나 | `lseek()` + `read()`를 여러 번 |
| 큰 파일의 아무 위치나, 더 쉽게 | **`mmap()`**으로 매핑하고 **포인터로 바로 접근** |

### 개념

- 가상 메모리 = **디스크에 저장된 N바이트짜리 연속 배열**이라고 생각한다.
- 그 내용이 물리 메모리(**DRAM 캐시**)에 캐시된다.
- 캐시 블록 단위를 **페이지**(P = 2^p바이트)라고 한다.

| 가상 페이지(VP) 상태 | 뜻 |
|---|---|
| **미할당** (unallocated) | 아직 만들어지지 않음. 디스크 공간도 없음 |
| **캐시됨** (cached) | 할당됐고 물리 메모리에 올라와 있음 |
| **캐시 안 됨** (uncached) | 할당됐지만 디스크에만 있음 |

### DRAM 캐시가 이렇게 설계된 이유: 엄청난 미스 비용

DRAM은 SRAM보다 약 **10배**, 디스크는 DRAM보다 약 **10,000배** 느리다. 그래서:

- **큰 페이지** 크기: 보통 **4KB**, 가끔 4MB
- **완전 연관** (fully associative): 어떤 VP든 어떤 PP에나 놓을 수 있음 → 큰 매핑 함수(페이지 테이블)가 필요
- 정교하고 비싼 교체 알고리즘 → 하드웨어로 만들기엔 너무 복잡해서 **OS 소프트웨어**가 함
- **write-back** (write-through 아님)

### 페이지 테이블

**페이지 테이블** = 가상 페이지를 물리 페이지로 매핑하는 **PTE(페이지 테이블 항목) 배열**. **프로세스마다** 하나씩 있는 커널 자료구조이고 DRAM에 있다.

```
 PTE    Valid   물리 페이지 번호 또는 디스크 주소
PTE 0     0     null            ← 미할당
PTE 1     1     PP 0 (VP 1)     ← 캐시됨 (DRAM에 있음)
PTE 2     1     PP 1 (VP 2)
PTE 3     0     디스크 (VP 3)   ← 캐시 안 됨
PTE 4     1     PP 3 (VP 4)
PTE 5     0     null
PTE 6     0     디스크 (VP 6)
PTE 7     1     PP 2 (VP 7)
```

| 용어 | 뜻 |
|---|---|
| **페이지 히트** | 접근한 VM 워드가 물리 메모리에 있음 (DRAM 캐시 히트), Valid = 1 |
| **페이지 폴트** | 접근한 VM 워드가 물리 메모리에 없음 (DRAM 캐시 미스), Valid = 0 |

## 4. 페이지 폴트와 요구 페이징 — `lazy_alloc.c`

### 페이지 폴트 처리 순서 (슬라이드 23~26)

1. VP 3에 접근 → PTE 3의 Valid = 0 → **페이지 폴트** (예외 발생)
2. 커널의 **페이지 폴트 핸들러**가 내쫓을 희생자(victim)를 고름 (예: VP 4)
3. VP 4를 (수정됐으면) 디스크에 쓰고, VP 3을 그 물리 페이지로 복사, PTE 갱신
4. 폴트를 일으킨 **명령어를 다시 실행** → 이번엔 페이지 히트

**요구 페이징 (demand paging)**: 미스가 날 때까지 기다렸다가 페이지를 DRAM에 복사하는 방식.

**페이지 할당**: 새 가상 페이지(VP 5)를 할당하면 디스크에 자리를 만들고 PTE가 그곳을 가리키게 할 뿐, 물리 페이지는 아직 쓰지 않는다.

### 실습: malloc은 물리 메모리를 바로 주지 않는다 (arm64)

```c
p = malloc(256MB);          // 가상 주소 공간만 예약
memset(p, 1, SIZE / 2);     // 절반만 실제로 접근
memset(p, 1, SIZE);         // 전부 접근
```

```
$ ./lazy_alloc
start          : RSS =    1024 kB, faults = 84
after malloc   : RSS =    1224 kB, faults = 86
touch half     : RSS =  132296 kB, faults = 8278
touch all      : RSS =  263368 kB, faults = 16470
```

- **RSS**(Resident Set Size) = 실제로 물리 메모리에 올라온 크기 (`/proc/self/status`의 `VmRSS`).
- 256MB를 `malloc`해도 RSS는 **거의 그대로**다. 가상 주소만 받은 상태 = **게으른 할당**.
- **접근한 만큼** 페이지 폴트가 나면서 RSS가 128MB, 256MB로 늘어난다 = **요구 페이징**.
- 폴트 수 = 디스크 I/O 없이 처리된 minor fault(`getrusage`의 `ru_minflt`). 128MB ÷ 4KB = 32,768 페이지인데 폴트는 약 8,200번이다. 이 커널은 **16KB 단위 THP(mTHP)**가 켜져 있어 한 번의 폴트에 4페이지씩 할당하기 때문이다. 확인: `/sys/kernel/mm/transparent_hugepage/hugepages-16kB/enabled` = `[always]` → 128MB ÷ 16KB = 8,192.

### 지역성(locality)이 살린다

가상 메모리는 매우 비효율적으로 보이지만 **지역성** 덕분에 잘 동작한다.

- 프로그램은 어느 시점에 일부 가상 페이지(**작업 집합, working set**)만 집중적으로 쓴다.
- 시간 지역성이 좋을수록 작업 집합이 작다.

| 조건 | 결과 |
|---|---|
| 작업 집합 크기 < 메인 메모리 크기 | 처음의 필수 미스(compulsory miss) 뒤에는 좋은 성능 |
| **모든 프로세스 작업 집합 합 > 메인 메모리** | **스래싱 (thrashing)**: 페이지가 계속 들락날락하며 성능 붕괴 |

## 5. VM은 메모리 관리 도구 — `maps.c`

- **핵심: 프로세스마다 자기만의 가상 주소 공간**이 있다. 메모리를 단순한 선형 배열로 본다.
- 매핑 함수가 주소를 물리 메모리 여기저기로 흩어 놓는다. 잘 고른 매핑은 지역성을 높인다.

```
프로세스 1          물리 메모리 (DRAM)        프로세스 2
VP 1 ──────────→ PP 2
VP 2 ──────────→ PP 6 ←────────────────── VP 1   (예: 읽기 전용 라이브러리 코드)
                 PP 8 ←────────────────── VP 2
```

| 쓰임 | 설명 |
|---|---|
| 메모리 할당 단순화 | 어떤 VP든 어떤 PP에 매핑 가능. 같은 VP가 시점마다 다른 PP에 있을 수도 |
| 코드·데이터 공유 | 여러 VP를 **같은 PP**에 매핑 (위 그림의 PP 6) |
| **링킹 단순화** | 모든 프로그램이 비슷한 가상 주소 공간을 가짐. 코드·데이터·힙이 항상 같은 주소에서 시작 (0x400000) |
| **로딩 단순화** | `execve`는 `.text`, `.data`용 가상 페이지만 할당. 실제 내용은 VM 시스템이 **필요할 때 페이지 단위로** 복사 |

### 실습: 이 프로세스의 가상 메모리 영역 (arm64)

```
$ ./maps          # /proc/self/maps 출력
00400000-00401000 r-xp 00000000 ... /w/01_주소공간/maps          ← .text (읽기+실행)
0041f000-00420000 r--p 0000f000 ... /w/01_주소공간/maps          ← 읽기 전용 데이터
00420000-00421000 rw-p 00010000 ... /w/01_주소공간/maps          ← .data/.bss (읽기+쓰기)
0b901000-0b922000 rw-p 00000000 00:00 0      [heap]              ← malloc 영역
ffffaad10000-ffffaae9c000 r-xp ... /usr/lib/aarch64-linux-gnu/libc.so.6   ← 공유 라이브러리 코드
ffffaaeac000-ffffaaeb0000 r--p ... /usr/lib/aarch64-linux-gnu/libc.so.6
ffffaaeb0000-ffffaaeb2000 rw-p ... /usr/lib/aarch64-linux-gnu/libc.so.6   ← libc의 .data
ffffaaec8000-ffffaaeef000 r-xp ... /usr/lib/aarch64-linux-gnu/ld-linux-aarch64.so.1  ← 동적 링커
ffffaaf04000-ffffaaf06000 r-xp 00000000 00:00 0      [vdso]
ffffcb1cb000-ffffcb1ec000 rw-p 00000000 00:00 0      [stack]
```

- 각 줄이 하나의 **영역**(커널의 `vm_area_struct`)이다: 시작-끝 주소, 권한, 파일 오프셋, 원본 파일.
- 권한 `r-xp`의 `p`는 **private**(COW), `s`면 shared.
- 실행 파일, libc, 동적 링커가 **파일에서 매핑**되고, 힙과 스택은 파일 없는 **익명 매핑**이다.
- 5강 슬라이드 22의 메모리 배치와 같다.

## 6. VM은 메모리 보호 도구 — `protect.c`

**PTE에 권한 비트**를 더하고, MMU가 접근할 때마다 검사한다.

| 프로세스 i | SUP | READ | WRITE | EXEC | 주소 |
|---|:---:|:---:|:---:|:---:|---|
| VP 0 | No | Yes | **No** | Yes | PP 6 |
| VP 1 | No | Yes | Yes | No | PP 4 |
| VP 2 | **Yes** | Yes | Yes | No | PP 2 |

- **SUP**: 커널(슈퍼바이저) 모드에서만 접근 가능. 사용자 코드가 접근하면 에러.
- 권한을 어기면 **보호 폴트** → 커널이 보통 **SIGSEGV**를 보낸다.

```c
char *s = "software";           // 문자열 리터럴 → .rodata (WRITE = No)
s[0] = 'h';                     // 보호 폴트
```

```
$ ./protect
child killed by signal 11 (Segmentation fault)
```

자식이 시그널 11로 죽은 것을 4강의 `WIFSIGNALED`/`WTERMSIG`로 확인했다. 과제 2에서 실행 중이 아니라 **디스크의 파일**을 고친 이유가 이것이다.

## 7. 공유 객체와 Copy-on-Write — `cow.c`

### 공유 객체 (shared object)

- 프로세스 1이 공유 객체(예: `libc.so`)를 매핑하고, 프로세스 2도 같은 객체를 매핑하면 **같은 물리 페이지**를 공유한다.
- 두 프로세스의 **가상 주소는 달라도 된다.**

### 사적 Copy-on-Write 객체

- 두 프로세스가 **private COW 객체**를 매핑: 영역은 private COW로 표시되고, PTE는 **읽기 전용**으로 표시된다.
- 처음엔 같은 물리 페이지를 공유한다.
- 한쪽이 그 페이지에 **쓰면** → 보호 폴트 → 핸들러가 **새 읽기/쓰기 페이지를 만들어 복사** → 명령어 재실행.
- **복사를 가능한 한 늦춘다.** 쓰지 않으면 끝까지 복사하지 않는다.

### 실습: fork 후 같은 가상 주소, 다른 값 (arm64)

```c
int value = 100;
char *big = malloc(64MB); memset(big, 1, 64MB);  // 부모에서 미리 전부 할당

if (fork() == 0) {
    value = 200;                                  // 쓰기 → 이 페이지만 복사
    for (i = 0; i < 64MB; i += 4096) big[i] = 2;  // 페이지마다 쓰기 → 페이지마다 복사
    ...
}
```

```
$ ./cow
child : &value = 0x420068, value = 200
child : write 64MB -> 16384 faults (64MB / 4KB = 16384 pages)
parent: &value = 0x420068, value = 100
parent: big[0] = 1 (자식의 쓰기가 보이지 않음)
```

- 부모와 자식의 `&value`가 **똑같은 가상 주소**인데 값은 다르다. 같은 VP가 이제 **서로 다른 PP**에 매핑돼 있기 때문이다.
- 자식이 64MB에 쓰자 **16,384번**(= 64MB ÷ 4KB) 폴트가 났다. 쓴 페이지마다 COW 복사가 일어났다는 증거다.
- 자식이 쓴 내용은 부모에게 보이지 않는다.

## 8. fork와 execve 다시 보기

### fork

VM과 메모리 매핑으로 `fork`가 각 프로세스에 **사적 주소 공간**을 주는 방법을 설명할 수 있다.

1. 새 프로세스용 가상 주소 공간 생성
2. 현재 프로세스의 `mm_struct`, `vm_area_struct`, 페이지 테이블을 **그대로 복사**
3. 두 프로세스의 모든 페이지를 **읽기 전용**으로 표시
4. 두 프로세스의 모든 `vm_area_struct`를 **private COW**로 표시
5. 리턴하면 두 프로세스는 똑같은 가상 메모리를 가짐
6. 이후 쓰기가 일어나면 COW로 새 페이지를 만듦

→ `fork`가 빠른 이유: 메모리를 **복사하지 않고** 페이지 테이블만 복사한다.

### execve

현재 프로세스에서 새 프로그램 `a.out`을 실행할 때:

1. 기존 영역의 `vm_area_struct`와 페이지 테이블을 **해제**
2. 새 영역의 `vm_area_struct`와 페이지 테이블을 **생성**
3. PC를 `.text`의 **진입점**으로 설정
4. 리눅스는 필요할 때 코드·데이터 페이지를 **폴트로 불러옴**

| 영역 | 종류 | 원본 |
|---|---|---|
| 사용자 스택 | private, **demand-zero** | 익명 파일 |
| 공유 라이브러리 매핑 영역 | **shared, file-backed** | `libc.so`의 `.text`, `.data` |
| 런타임 힙 (malloc) | private, demand-zero | 익명 파일 |
| `.bss` | private, demand-zero | 익명 파일 |
| `.data` | **private, file-backed** | `a.out`의 `.data` |
| `.text` | private, file-backed | `a.out`의 `.text` |

- **file-backed**: 처음 접근하면 파일 내용으로 채움. **demand-zero (익명)**: 처음 접근하면 0으로 채운 페이지를 줌.
- `.bss`가 파일 공간을 차지하지 않아도 되는 이유가 이것이다 (5강).

## 9. mmap — `03_mmap/`

```c
void *mmap(void *start, int len, int prot, int flags, int fd, int offset);
```

| 인자 | 뜻 |
|---|---|
| `start` | 원하는 시작 주소. **0(NULL)이면 커널이 고름** |
| `len` | 매핑할 바이트 수 |
| `prot` | `PROT_READ`, `PROT_WRITE`, ... |
| `flags` | `MAP_ANON`(파일 없음), `MAP_PRIVATE`(COW), `MAP_SHARED`(공유), `MAP_FIXED`(start 강제) |
| `fd`, `offset` | fd로 지정한 파일의 `offset`바이트부터 |
| 반환 | 매핑된 영역의 시작 포인터 (`start`와 다를 수 있음), 실패 시 `MAP_FAILED` |

파일의 `offset`부터 `len`바이트를, 프로세스 가상 메모리의 `start`(또는 커널이 고른 주소)부터 `len`바이트에 매핑한다.

### `mmapcopy.c` — read 없이 파일을 stdout으로 (슬라이드 10)

```c
fd = open(argv[1], O_RDONLY, 0);
fstat(fd, &stat);                                   // 파일 크기
bufp = mmap(NULL, stat.st_size, PROT_READ, MAP_PRIVATE, fd, 0);
write(1, bufp, stat.st_size);                       // 매핑된 메모리를 그대로 write
```

```
$ ./mmapcopy in.txt
mmap test
```

사용자 공간 버퍼로 `read`해서 복사하는 단계가 없다. 파일 페이지가 그대로 내 주소 공간에 보인다.

### `mmap_shared.c` — MAP_PRIVATE vs MAP_SHARED (과제 2를 mmap으로)

```c
p = mmap(NULL, size, PROT_READ | PROT_WRITE, flags, fd, 0);
hit = memmem(p, size, "software", 8);
memcpy(hit, "hackers!", 8);          // 포인터로 바로 수정 (read/lseek/write 없음)
```

```
$ ./mmap_shared
after MAP_PRIVATE: Hello the school of software
after MAP_SHARED : Hello the school of hackers!
```

| 플래그 | 쓰기 결과 |
|---|---|
| `MAP_PRIVATE` | **COW**: 쓰는 순간 내 사본이 생김 → 파일은 그대로 |
| `MAP_SHARED` | 쓰기가 **파일에 반영**되고 같은 파일을 매핑한 다른 프로세스에도 보임 |

과제 2는 `read` → 버퍼 수정 → `pwrite`로 했지만, `MAP_SHARED`로 매핑하면 **포인터로 바로 고칠 수도 있다.**

## 10. 스택과 주소 변환

### C 스택

커널이 스택을 관리한다고 했지만, 정확히는 **커널이 MMU를 설정해서** 스택을 관리한다.

- 프로세스 생성 시 커널은 스택이 얼마나 커질 수 있는지 정하고, 스택 페이지를 **"존재하지 않음, 하지만 읽기·쓰기 가능"**으로 표시한다.
- 스택이 자라서 새 페이지에 닿으면 **페이지 폴트가 새 페이지를 할당**한다.
- 그래서 프로그램은 스택 크기를 직접 정하지 않아도 된다 (힙의 break와 비교).

### 페이지 테이블로 주소 변환

```
가상 주소 (n비트)  [   VPN (n-p비트)   |  VPO (p비트) ]
                         │                    │
 PTBR(페이지 테이블 시작) + VPN → PTE          │
                         │                    │
               Valid = 0 → 페이지 폴트         │ 그대로 복사
               Valid = 1 → PPN                │
                         ▼                    ▼
물리 주소 (m비트)  [   PPN (m-p비트)   |  PPO (p비트) ]
```

- **PTBR**(Page Table Base Register): 현재 프로세스 페이지 테이블의 물리 주소. x86-64에서는 **CR3**.
- **VPO = PPO**: 페이지 안 위치는 바뀌지 않는다. **VPN → PPN만** 바꾼다.

### x86-64의 4단계 페이지 테이블

```
선형 주소 64비트:
[63..48 부호 확장][47..39: 9][38..30: 9][29..21: 9][20..12: 9][11..0: 12]
                     PML4      PDPT       PD         PT        페이지 안 오프셋
CR3 → PML4 table → page-directory-pointer table → page directory → page table → 4KB 페이지
```

- 각 단계 테이블은 2^9 = **512개** 항목, 항목당 8바이트 → 테이블 하나 = **4KB = 페이지 하나**.
- 4 × 9 + 12 = **48비트** 가상 주소. 위 16비트는 47번 비트의 부호 확장.
- 왜 여러 단계? 48비트를 테이블 하나로 만들면 2^36개 × 8B = 512GB. 여러 단계로 나누면 **실제로 쓰는 영역의 테이블만** 만들면 된다.

### 예제: 위 `address.c`의 `.data` 주소 0x404030

| 부분 | 계산 | 값 |
|---|---|---|
| VPO (아래 12비트) | 0x404030 & 0xFFF | **0x030** |
| VPN | 0x404030 >> 12 | **0x404** |
| PT 인덱스 (비트 20..12) | 0x404 & 0x1FF | 0x004 |
| PD 인덱스 (비트 29..21) | (0x404030 >> 21) & 0x1FF | 0x002 |
| PDPT, PML4 인덱스 | | 0, 0 |

| 1 | 가상 주소 방식에서 주소 변환은 MMU가 한다 | **O** |

| 8 | `fork` 직후 부모와 자식의 메모리는 물리적으로 복사되어 있다 | **X** — 페이지 테이블만 복사, 읽기 전용 + COW. 쓸 때 복사 |
| 9 | fork 후 같은 변수의 가상 주소가 부모와 자식에서 같아도 값은 다를 수 있다 | **O** — 실습 `&value = 0x420068`, 100 vs 200 |
| 10 | `.bss`와 스택은 file-backed 영역이다 | **X** — demand-zero(익명 파일) |
| 11 | `MAP_PRIVATE`로 매핑한 메모리에 쓰면 파일이 바뀐다 | **X** — COW 사본만 바뀜. 파일 반영은 `MAP_SHARED` |

| 14 | `.rodata`에 쓰면 PTE의 권한 검사에 걸려 SIGSEGV가 난다 | **O** |

## 한 줄 요약

> **가상 메모리**는 프로세스마다 같은 모양의 주소 공간을 주고, **MMU**가 **페이지 테이블**(프로세스별 PTE 배열, PTBR/CR3)로 **VPN → PPN**을 바꾼다(VPO = PPO). DRAM은 디스크의 **캐시**라 페이지가 크고(4KB) 완전 연관이며, 없는 페이지에 접근하면 **페이지 폴트** 후 명령어를 재실행한다(**요구 페이징**, `malloc`은 게으른 할당). PTE의 **권한 비트**로 보호(SIGSEGV)하고, 같은 PP를 매핑해 공유하며, `fork`는 페이지를 읽기 전용으로 공유하다 **쓸 때 복사(COW)**한다. `execve`는 영역을 file-backed / demand-zero로 새로 만들고, **`mmap`**은 파일을 주소 공간에 직접 매핑한다(`MAP_PRIVATE` = COW, `MAP_SHARED` = 파일 반영).

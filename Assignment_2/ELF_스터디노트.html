7F 45 4C 46 부터 읽는 ELF 해부 노트

과제에 쓰인 test 바이너리의 실제 바이트를 그대로 펼쳐 놓고, ELF 구조 → 과제 코드 → 링킹·I/O 개념을 한 줄로 이었습니다. 모든 오프셋과 값은 x86-64 리눅스에서 readelf, xxd로 직접 확인한 값입니다.

제출물: 20221787.zip대상: test (ELF64, PIE, x86-64)강의: 5주차 링킹 · 6주차 ELF/입출력

01과제 한눈에 보기

과제는 실행 파일 안의 문자열 상수를 디스크 위에서 직접 고치는 것입니다. 프로그램이 하는 일은 다섯 단계입니다.

  1. 파일 열기open(path, O_RDWR) 읽고 쓰기 둘 다
  2. 통째로 읽기lseek로 크기 → read 반복
  3. ELF 검사크기 ≥ 64, 매직 7F 'E' 'L' 'F', ELF64
  4. .rodata 찾기e_shoff → 섹션 헤더 → shstrtab + sh_name
  5. 덮어쓰기"software" 위치에 pwrite로 "hackers!" 8바이트

02ELF 파일 지도

ELF 파일은 헤더 → (프로그램 헤더 테이블) → 섹션 내용들 → 섹션 헤더 테이블 순서로 놓입니다. 헤더가 지도 역할을 해서, 나머지 위치는 전부 헤더에서 출발해 찾아갑니다. 아래는 과제 test(15,960바이트)의 실제 배치입니다.

readelf -S -W test 결과에서 뽑은 오프셋. 0x3698 + 31×64 = 15,960 = 파일 크기와 정확히 일치합니다.
기억할 것

세 가지 ELF 파일 종류(.o 재배치 가능, a.out 실행, .so 공유)는 모두 같은 형식입니다. 섹션 헤더 테이블은 링킹용(재배치 파일에 필수), 프로그램 헤더 테이블은 실행용(실행 파일에 필수)입니다.

03ELF 헤더 64바이트 직접 읽기

아래는 test의 첫 64바이트입니다. 바이트를 누르면 어느 필드인지, 리틀 엔디언으로 어떻게 읽히는지 나옵니다. 처음엔 e_shoff가 선택되어 있습니다.

리틀 엔디언 읽는 법

파일에 98 36 00 00 00 00 00 00로 저장된 8바이트는 뒤에서부터 읽어 0x0000000000003698입니다. x86-64는 낮은 자리 바이트를 낮은 주소에 둡니다. 그래서 C에서 hdr->e_shoff로 구조체를 덮어 읽으면 변환 없이 바로 0x3698이 나옵니다.

04섹션 이름 찾기: shstrtab + sh_name

가장 많이 헷갈리는 부분입니다. 섹션 헤더에는 이름 문자열이 없고, sh_name이라는 오프셋 숫자만 있습니다. 이름은 .shstrtab 섹션에 \0으로 구분되어 모여 있습니다.

// ① 헤더에서 섹션 헤더 테이블 위치
sht      = buffer + hdr->e_shoff;                 // 0x3698
// ② e_shstrndx(=30)번 섹션이 .shstrtab
shstrtab = buffer + sht[hdr->e_shstrndx].sh_offset; // 0x357a
// ③ i번 섹션의 이름 = shstrtab + sh_name
name     = shstrtab + sht[i].sh_name;

// 18번 섹션 헤더 (파일 0x3698 + 18×64 = 0x3b18)
c5 00 00 00 01 00 00 00  02 00 00 00 00 00 00 00   sh_name=0xc5  sh_type=PROGBITS  sh_flags=A
00 20 00 00 00 00 00 00  00 20 00 00 00 00 00 00   sh_addr=0x2000  sh_offset=0x2000
21 00 00 00 00 00 00 00  00 00 00 00 00 00 00 00   sh_size=0x21

// .shstrtab(0x357a) + 0xc5 = 0x363f 에 있는 문자열
".rodata\0"   → strcmp(name, ".rodata") == 0 이므로 찾음
실제 test 파일의 바이트. .shstrtab 자신도 섹션이므로 자기 이름(sh_name=0x11 → ".shstrtab")을 자기 안에 갖고 있습니다.
덤으로 알아 두기

이 파일의 .shstrtab에는 ".plt"라는 문자열이 따로 없습니다. 링커가 ".rela.plt"의 꼬리를 공유시켜 .plt의 sh_name이 그 문자열 중간을 가리키게 했기 때문입니다. 이름을 "오프셋"으로 두는 설계 덕분에 가능한 절약입니다.

05.rodata 패치 시뮬레이터

.rodata는 파일 오프셋 0x2000부터 0x21(=33)바이트입니다. 버튼을 눌러 프로그램이 바꾸는 8바이트를 확인해 보세요.

$ ./test
Hello the school of software

바이트에 숨은 사실 세 가지

  • 앞 4바이트 01 00 02 00은 문자열이 아니라 libc의 _IO_stdin_used 상수입니다. 그래서 문자열은 0x2004에서 시작하고, "software"는 0x2004 + 20 = 0x2018에 있습니다.
  • 문자열 끝에 \n이 없습니다. 원본 C 코드는 printf("Hello the school of software\n")지만, gcc가 이를 puts("Hello the school of software")로 바꿔 줄바꿈을 puts가 붙입니다. objdump -d로 보면 main이 puts@plt를 호출합니다.
  • 길이가 같아서 덮어쓰기만 하면 됩니다. "software"와 "hackers!"는 둘 다 8바이트입니다. 길이가 다르면 뒤쪽 데이터 오프셋과 코드 안의 주소 참조(RIP 상대 주소 lea 0xea1(%rip))가 전부 틀어집니다.
함정

"hackers!"를 쓸 때 sizeof("hackers!")(=9)를 쓰면 \0까지 9바이트를 씁니다. 문자열이 "software"로 끝나는 경우엔 우연히 괜찮지만, "software engineering"처럼 중간에 있으면 "hackers!\0engineering"이 되어 문자열이 잘립니다. 그래서 코드는 strlen(=8)만 씁니다.

06내 코드 해설 (20221787.c)

제공된 editro를 뼈대로 쓰고, 과제 요구(ELF 검사 함수, .rodata 수정)와 안전장치를 더했습니다. 함수별로 열어 보세요.

is_elf()과제 요구 ①: 진짜 ELF인지 검사 
if (length < (off_t)sizeof(Elf64_Ehdr))        // 64B보다 작으면 헤더조차 못 읽음
    return 0;
if (memcmp(hdr->e_ident, ELFMAG, SELFMAG) != 0) // "\177ELF", 4바이트 비교
    return 0;
if (hdr->e_ident[EI_CLASS] != ELFCLASS64)      // Elf64_* 구조체로 읽으므로 64비트만
    return 0;

순서가 중요합니다. 크기를 먼저 보지 않으면 5바이트짜리 텍스트 파일에서 헤더를 읽다가 버퍼 밖을 읽습니다. 32비트 ELF는 Elf32_Ehdr가 52바이트이고 필드 크기가 달라서, 64비트 구조체로 읽으면 엉뚱한 값이 나옵니다.

read_file()파일을 통째로 메모리에 
*length = lseek(fd, 0, SEEK_END);   // 끝으로 이동한 위치 = 파일 크기
lseek(fd, 0, SEEK_SET);             // 다시 처음으로
while (total < *length) {
    n = read(fd, buffer + total, *length - total);
    if (n <= 0) ...                   // 0 = EOF, -1 = 에러
    total += n;                      // read는 요청보다 적게 읽을 수 있음(short count)
}

원본 editro는 read를 한 번만 부르고, malloc 실패도 확인하지 않았습니다. 6주차 슬라이드의 read 반환값 규칙(0: EOF, >0: 읽은 바이트, <0: 에러)을 그대로 적용했습니다.

{
    return offset <= length && size <= length - offset;  // offset+size 오버플로 방지
}
...
if (!in_file(hdr->e_shoff, e_shnum * sizeof(Elf64_Shdr), length)) return NULL;

매직만 맞고 내용이 망가진 파일(잘린 파일 등)이 들어와도 버퍼 밖을 읽지 않도록, 헤더가 가리키는 모든 범위가 파일 안에 있는지 확인합니다. offset + size > length로 쓰면 큰 값에서 덧셈이 넘쳐 검사를 통과할 수 있어 뺄셈 형태로 썼습니다.

patch_rodata()과제 요구 ②: 찾아서 바꾸고 파일에 쓰기 
for (i = 0; i + len <= rodata->sh_size; i++) {     // .rodata 범위 안에서만 검색
    if (memcmp(&section[i], TARGET_STR, len) != 0) continue;
    memcpy(&section[i], REPLACE_STR, len);             // 메모리 버퍼 수정
    pwrite(fd, &section[i], len, rodata->sh_offset + i); // 파일의 같은 위치에 기록
    count++;
    i += len - 1;                                      // 바꾼 부분은 건너뜀
}
  • 왜 strstr이 아니라 memcmp? .rodata에는 \0이 섞여 있습니다(앞의 01 00 02 00처럼). strstr은 첫 \0에서 멈춰 그 뒤를 못 찾습니다.
  • 왜 파일 전체가 아니라 .rodata만? 과제가 .rodata 수정이고, .symtab이나 .comment에 같은 바이트열이 있어도 건드리면 안 됩니다.
  • 파일 오프셋 = sh_offset + i. sh_addr(실행 시 가상주소)가 아니라 sh_offset(파일 위치)을 써야 합니다. 이 파일은 둘이 0x2000으로 같지만 일반적으로는 다릅니다(.data는 addr 0x4000, offset 0x3000).
  • pwrite는 lseek + write를 한 번에 하는 시스템 콜이며 파일 위치를 바꾸지 않습니다. 바뀐 8바이트만 씁니다.
Makefile학번 이름 실행 파일 생성 
CC=gcc
CFLAGS=-Wall
TARGET=20221787
OBJ=20221787.o

$(TARGET): $(OBJ)              # 첫 타깃 = make만 쳤을 때 만들어지는 것
	$(CC) -o $@ $^             # $@ = 타깃 이름, $^ = 모든 의존 파일

%.o: %.c 20221787.h            # 패턴 규칙: 헤더가 바뀌어도 다시 컴파일
	$(CC) $(CFLAGS) -c -o $@ $<  # $< = 첫 번째 의존 파일

clean:
	rm -f *.o $(TARGET)        # -f: 파일이 없어도 에러 없이

원본 editro Makefile은 rm *.o를 두 줄로 써서, .o가 없으면 첫 줄에서 실패해 실행 파일이 안 지워졌습니다.

원본 editro의 숨은 버그

슬라이드 예시 화면의 Size = 0x00000033은 사실 16진수가 아닙니다. editro는 "0x%08ld"로 10진수를 찍고 앞에 0x만 붙였습니다. 실제 크기는 33바이트 = 0x21이고, readelf -S도 0x21이라고 합니다. 제 코드는 %08lX로 고쳤습니다.

07섹션 vs 세그먼트: 왜 파일은 고칠 수 있고 실행 중엔 못 고치나

링커는 섹션 단위로 보고, 로더(execve)는 세그먼트(프로그램 헤더의 LOAD 항목) 단위로 메모리에 올립니다. readelf -l test의 LOAD 세그먼트는 네 개입니다.

파일 오프셋권한들어 있는 섹션
0x0000RELF 헤더, .interp, .dynsym, .rela.* …
0x1000R E.init .plt .text .fini (코드)
0x2000R.rodata .eh_frame_hdr .eh_frame
0x2db8RW.init_array .dynamic .got .data .bss

.rodata가 들어 있는 세그먼트는 읽기 전용(R)으로 매핑됩니다. 그래서 C 코드에서 char *s = "software"; s[0] = 'h';를 하면 Segmentation fault가 납니다. 과제는 실행 중이 아니라 디스크의 파일을 고치므로, 다음 실행 때 로더가 바뀐 바이트를 그대로 메모리에 올립니다.

메모리 배치 복습 (5주차 슬라이드 22)

읽기 전용 코드 세그먼트(.init, .text, .rodata) → 읽기/쓰기 데이터 세그먼트(.data, .bss) → 힙(brk, malloc) → … → 공유 라이브러리 매핑 영역 → 사용자 스택(%rsp) → 커널 메모리.

08링킹 핵심 (5주차)

링커가 하는 두 가지 일

  1. 심볼 해석(symbol resolution): 각 심볼 참조를 정확히 하나의 정의와 연결합니다. 정의는 어셈블러가 .symtab에 기록합니다.
  2. 재배치(relocation): 여러 .o의 같은 섹션을 합치고, 심볼을 최종 주소로 옮긴 뒤 모든 참조를 고칩니다. 고칠 위치는 .rel.text, .rel.data에 있습니다.
# objdump -r -d main.o (재배치 전)
 9: bf 00 00 00 00   mov $0x0,%edi      # a: R_X86_64_32  array      (절대 주소)
 e: e8 00 00 00 00   callq 13 <main+0x13> # f: R_X86_64_PC32 sum-0x4  (PC 상대)
# 링크 후
4004d9: bf 18 10 60 00   mov $0x601018,%edi    # &array
4004de: e8 05 00 00 00   callq 4004e8 <sum>    # 0x4004e8 - 4 - 0x4004df = 0x05
PC32 계산: ADDR(sum) + addend(-4) - 참조 위치(0x4004df). 다음 명령어 주소(0x4004e3)로부터의 거리와 같습니다.

심볼 종류와 강/약 규칙

  • 전역 심볼: 모듈이 정의하고 다른 모듈이 참조 가능 (static 아닌 함수/전역변수). 외부 심볼: 참조하지만 다른 곳에서 정의. 지역 심볼: static 함수/전역변수. 함수 안의 일반 지역변수는 스택에 있으므로 링커 심볼이 아닙니다.
  • 함수 안 static int x는 .data/.bss에 들어가고, 이름 충돌을 막으려 x.1, x.2처럼 고유한 지역 심볼이 됩니다.
  • 강한 심볼 = 함수, 초기화된 전역. 약한 심볼 = 초기화 안 된 전역.
  • 규칙 1: 강한 심볼 여러 개 → 링크 에러. 규칙 2: 강 1 + 약 여러 개 → 강한 것 선택. 규칙 3: 약한 것만 여러 개 → 임의 선택 (-fno-common으로 막음).
  • 함정: int x; int y;(p1.c)와 double x;(p2.c) → p2에서 x에 8바이트를 쓰면 y까지 덮어씁니다.

라이브러리

  • 정적 라이브러리(.a): .o 묶음 + 인덱스(ar rs libc.a ...). 필요한 .o만 실행 파일에 복사. 링커는 명령행 순서로 스캔하며 미해결 참조 목록을 유지하므로 라이브러리는 명령행 끝에 둡니다.
  • 공유 라이브러리(.so): 로드 시(ld-linux.so가 처리) 또는 실행 중(dlopen/dlsym/dlclose) 링크. 디스크·메모리 중복 제거, 라이브러리만 업데이트 가능. 생성: gcc -shared -fpic.

09Unix I/O 핵심 (6주차)

  • 모든 것은 파일: 파일 = m바이트의 연속. 장치(/dev/null, /dev/urandom)와 커널 정보(/proc)도 파일로 접근.
  • 파일 디스크립터: 프로세스의 열린 파일을 나타내는 작은 정수. 0 = stdin, 1 = stdout, 2 = stderr.
  • 권한 비트: rwxrwxrwx = 소유자/그룹/기타. 8진수 750 = rwxr-x---, 664 = rw-rw-r--.
  • 시스템 콜 실패 시 음수 반환 + errno 설정. perror("open") → open: No such file or directory.
